# fips-initramfs on NixOS

The NixOS implementation of what the rest of this repository does as a
`.deb`: a FIPS mesh node inside the initrd, so an encrypted root can be
unlocked over the mesh rather than over the local IP network. The
machine dials out to its bootstrap peers and needs no inbound
reachability, and it comes up at the same mesh address on every boot.

**Console passphrase entry is never disabled.** Every failure in this
path leaves the operator at the ordinary prompt.

This is a second implementation of the contract in
[../docs/porting.md](../docs/porting.md), not a repackaging of the
`.deb`. Nothing here is built with `dpkg`, there is no
`initramfs-tools` hook and no dropbear. What is the same is the part
that matters: a persistent identity separate from the host's, an
address the node is checked against at boot, and a failure policy that
always ends at the console prompt.

## What is different from the `.deb`, and why

| | `.deb` | NixOS |
| --- | --- | --- |
| Image generator | `initramfs-tools` hook | this module |
| Stage 1 | busybox scripts | systemd |
| SSH server | dropbear | OpenSSH, via `boot.initrd.network.ssh` |
| Unlock restriction | `command="cryptroot-unlock"` in the image's `authorized_keys` | root's login shell is systemd's password agent |
| Identity generated by | `postinst` | you, once, by hand |
| Expected address | written into the image at build time | derived in the initrd from the public key beside the private one |

Two of those are worth a sentence.

**The build-time checks are assertions, not warnings.** The `.deb`'s
hook must never exit non-zero, because a failing hook leaves
`initramfs-tools` half-configured and aborts the apt run. A NixOS module
has no such hazard, and the equivalent protection is better served by
refusing the switch: an assertion stops `nixos-rebuild` at the machine
you are standing at, rather than producing an image whose fault you find
out about after a reboot. Nothing at *boot* time is allowed to fail; see
below.

**The expected address is derived rather than recorded.** It cannot be
derived at build time here, because the identity deliberately lives
outside the Nix store and evaluation never sees it. Deriving it in the
initrd from `fips.pub`, which sits in the image beside `fips.key`, is
strictly the stronger check: it catches everything the recorded address
catches, and also a public key that does not match the private key next
to it.

## Setting it up

### 1. Add the flake

```nix
{
  inputs.fips-initramfs.url = "github:jmcorgan/fips-initramfs?dir=nixos";

  outputs = { nixpkgs, fips-initramfs, ... }: {
    nixosConfigurations.yourhost = nixpkgs.lib.nixosSystem {
      modules = [
        fips-initramfs.nixosModules.default
        {
          nixpkgs.hostPlatform = "x86_64-linux";
          nixpkgs.overlays = [ fips-initramfs.overlays.default ];
        }
        ./configuration.nix
      ];
    };
  };
}
```

The overlay is the FIPS flake's own, forwarded. A machine that already
runs the stage-2 FIPS daemon has it and needs only the module; the
initrd node then uses the same build as the daemon, which is the same
property the `.deb` gets by searching `/usr/bin` first.

`services.fips.initrd.package` overrides it if you get the daemon from
somewhere else.

### 2. Generate this node's identity

Once, by hand, and outside the flake. `fipsctl keygen` writes the pair
without contacting a daemon:

```sh
sudo install -d -m 0700 /var/lib/fips-initrd
sudo fipsctl keygen --dir /var/lib/fips-initrd
sudo chmod 0600 /var/lib/fips-initrd/fips.key
sudo chmod 0644 /var/lib/fips-initrd/fips.pub
```

**Outside the flake deliberately.** Anything inside a flake is copied
into the Nix store on every evaluation and the store is world readable,
so a key kept there is readable by every local user, and `git add` picks
it up where `.gitignore` cannot help once it is tracked. The module
refers to these files as absolute path *strings*, which Nix leaves
alone; only root reads them, at `nixos-rebuild switch` time.

The corollary is that **a fresh clone of your configuration cannot
rebuild this node's identity**. Back `/var/lib/fips-initrd` up, or
accept that losing it means a new mesh address and a new initrd host
key.

If the machine also runs FIPS, leave `/var/lib/fips/fips.key` alone.
The two identities are separate on purpose: this one ships inside an
unencrypted image on an unencrypted `/boot`, which is the exposure the
encrypted root exists to avoid, so it must not also be the key that
identifies the running machine on the mesh.

### 3. Generate the initrd SSH host key

```sh
sudo ssh-keygen -t ed25519 -N "" -f /var/lib/fips-initrd/ssh_host_ed25519_key
sudo chmod 0600 /var/lib/fips-initrd/ssh_host_ed25519_key
```

Not the host's stage-2 key, for the same reason.

### 4. Record the name you will connect to

```sh
cat /var/lib/fips-initrd/fips.pub          # npub1...
fipsctl address --key /var/lib/fips-initrd/fips.pub
```

**Record the npub.** It is the only thing you need afterwards and it
does not change. Connect to `<npub>.fips`, never to the address:
resolving that name through a FIPS DNS responder is what drives the
mesh lookup, and a bare address resolves nothing. The address is there
to be checked against, which is what the boot script does with it.

### 5. Encrypt the root, if it is not already

> **You cannot encrypt the root filesystem you are booted from.** Boot a
> NixOS installer image first, and back up regardless of which route you
> take.

In place, preserving the data, on LUKS2:

```sh
cryptsetup reencrypt --encrypt --reduce-device-size 64M /dev/disk/by-uuid/...
```

Or format and restore, which is slower and harder to get wrong:

```sh
mount /dev/disk/by-uuid/... /mnt && rsync -aHAX /mnt/ /backup/
cryptsetup luksFormat /dev/disk/by-uuid/...
cryptsetup open /dev/disk/by-uuid/... root
mkfs.ext4 /dev/mapper/root
mount /dev/mapper/root /mnt && rsync -aHAX /backup/ /mnt/
```

Then declare the mapping where your configuration names its
filesystems, normally `hardware-configuration.nix`:

```nix
boot.initrd.luks.devices."root".device = "/dev/disk/by-uuid/<the LUKS UUID>";
fileSystems."/" = { device = "/dev/mapper/root"; fsType = "ext4"; };
```

**Declare it once.** This module does not declare a LUKS device and
should not: two mappings for one device give two passphrase prompts,
run the KDF twice, and end with the loser failing on `Cannot use device
... which is in use`.

### 6. Set the options

```nix
services.fips.initrd = {
  enable = true;
  ssh.authorizedKeys = [ "ssh-ed25519 AAAA... you@workstation" ];
  ethernetInterfaces = [ "enp1s0" ];
};
```

`ethernetInterfaces` is per machine and there is no safe default. Get
the names from `ip -o link`; stage 1 uses the same predictable names as
the booted system. A name that does not exist is not an error anyone
sees: the daemon binds nothing and the transport is simply absent.

Leaving it empty is a legitimate answer for a machine whose only path to
the mesh is its default route, and the UDP transport carries that.

[examples/host.nix](examples/host.nix) is a fuller example, and is also
the flake's evaluation check.

### 7. Rebuild and reboot

```sh
sudo nixos-rebuild switch --flake .#yourhost
```

A missing key file fails the switch at `append-initrd-secrets`, which
is deliberate: generate the keys first. On the next boot the console
carries one of these, above the passphrase prompt:

```text
fips-initrd: node up at npub1....fips (fd...)
fips-initrd: WARNING: fips0 came up at fd..., not the expected fd...
fips-initrd: WARNING: fips0 has no global address after 20s; remote unlock is unavailable.
```

Then, from a machine with a running FIPS daemon on the same mesh:

```sh
ssh root@npub1....fips
```

The session lands on the passphrase prompt. Enter it and the boot
continues.

A host block is worth writing, because `ssh` otherwise offers every key
your agent holds:

```text
Host unlock-yourhost
    HostName npub1....fips
    User root
    IdentityFile ~/.ssh/id_ed25519_unlock
    IdentitiesOnly yes
```

## What the boot check does

`fips-mesh-check.service` runs after the daemon and before
`cryptsetup-pre.target`, so its verdict is on the console above the
passphrase prompt. It waits for the mesh interface to get a global
address, derives the address the identity in the image maps to, and
compares them.

**The comparison is the point.** A daemon whose key is missing from the
image generates a new identity and runs perfectly at an address nobody
is connecting to; a daemon whose TUN setup failed reports itself
degraded and keeps going. Neither is caught by asking whether the
daemon is alive, and both produce a machine that is discovered to be
unreachable only once it is remote and locked.

**Every path through it exits 0.** The wait is bounded by
`waitSeconds`, and its expiry does not stop the boot. Whatever it finds,
the machine arrives at its console prompt.

## Bring-up and diagnosis

The unlock session is the passphrase prompt and nothing else, which is
what you want in service and not what you want while it is still
failing. Two switches, both off by default:

```nix
services.fips.initrd.debug.consoleShell.enable = true;  # root shell on tty2
services.fips.initrd.debug.sshShell.enable = true;      # SSH lands on a shell
```

`consoleShell` puts a root shell on tty2, reached with Alt+F2 from the
prompt and left with Alt+F1. `fipsctl show peers`, `fipsctl show
transports`, `ip addr show fips0` and `journalctl -u fips-mesh` all work
there.

`sshShell` is the analogue of the `.deb`'s
`FIPS_FORCE_UNLOCK_COMMAND=no`. It replaces root's login shell with
bash, so a key that could previously only answer the prompt opens a root
shell with the mesh already attached — a foothold on the mesh and not
only on this machine. The module warns while it is on. Unlock from that
shell with `systemd-tty-ask-password-agent --query`.

`extraBin` adds tools to the initrd for the same purpose, and should
come back out afterwards: everything in it sits on an unencrypted
`/boot` and costs space in every kernel's initrd.

Common findings:

- **No global address on `fips0`.** The `tun` module is missing, or the
  daemon failed at startup. `journalctl -u fips-mesh` from the console
  shell has its first lines.
- **The address does not match.** The daemon is running under a
  generated identity, which means it did not find `/etc/fips/fips.key`.
  Check that `boot.initrd.secrets` put it there.
- **The node is up and unreachable anyway.** Almost always the peers.
  Auto-discovery finds a neighbour and attaches to it, which is a
  perfectly healthy node on a spanning tree with no anchor to the relays
  the rest of the mesh meets at. Give the initrd the same peers the
  booted system uses.
- **No network at all.** `networkKernelModules` does not include this
  machine's NIC driver. `lspci -k` names it.

## Options

| Option | Type | Default | What it is for |
| --- | --- | --- | --- |
| `enable` | bool | `false` | Turn the whole thing on |
| `package` | package | `pkgs.fips` | The daemon, normally from the forwarded overlay |
| `secretsDir` | str | `/var/lib/fips-initrd` | Where the identity and the initrd SSH host key live, outside the store |
| `ssh.authorizedKeys` | [str] | `[]` | Keys admitted to the initrd. At least one is required |
| `ethernetInterfaces` | [str] | `[]` | Wired interfaces for the L2 transport. Per machine |
| `peers` | [attrs] | public test mesh | Static bootstrap peers. Replace for anything you rely on |
| `settings` | attrs | `{}` | Merged over the generated node configuration |
| `interface` | str | `fips0` | Mesh TUN interface name |
| `waitSeconds` | int | `20` | How long to wait for the mesh address before reporting failure |
| `logLevel` | str | `info` | Daemon log level in stage 1 |
| `dns.enable` | bool | `false` | The `.fips` responder, off because nothing in the initrd resolves those names |
| `networkKernelModules` | [str] | common wired NICs | Loaded in the initrd. `tun` is added unconditionally |
| `extraBin` | [package] | `[]` | Extra tools on the initrd PATH, for the debug shell |
| `wifi.enable` | bool | `false` | Join an OPEN network in the initrd |
| `wifi.interface` | str | `""` | Required when wifi is on |
| `wifi.ssid` | str | `""` | Required when wifi is on. Open networks only, by design |
| `wifi.kernelModules` | [str] | `[]` | Name only this machine's driver; each drags in its firmware |
| `bluetooth.enable` | bool | `false` | BlueZ and the BLE transport |
| `bluetooth.adapter` | str | `hci0` | HCI adapter for the BLE transport |
| `bluetooth.kernelModules` | [str] | BlueZ set | Loaded in the initrd when Bluetooth is on |
| `debug.consoleShell.enable` | bool | `false` | Unauthenticated root shell on tty2 |
| `debug.sshShell.enable` | bool | `false` | SSH sessions get a shell instead of the prompt |

## Security

Everything in [the top-level README's security
section](../README.md#security-considerations) applies here unchanged.
The image is not encrypted and the node's private key is in it; treat
that identity as compromised the moment the machine is physically taken.
The passphrase leaves your machine, carried by the SSH session and by
FIPS's own encryption, so check the host key the first time you connect.
Anyone who knows the npub can reach the node, and the authorised key is
what stands between that and an unlock.

Two things are specific to this side:

- **The initrd SSH host key is a separate key**, generated in step 3.
  Reusing the stage-2 host keys would put them on the unencrypted
  `/boot`.
- **`debug.sshShell` widens the blast radius**, from "may answer a
  passphrase prompt" to "root on this machine and on the mesh". It is a
  bring-up switch.

## Status

**Not yet exercised as widely as the `.deb`.** The design has been run
on NixOS: a machine with an encrypted root, reached over the mesh in
stage 1 and unlocked with nothing typed at its console. The module in
this directory is that configuration generalised — per-host names turned
into options, and the address comparison added, which the original did
not have.

What that means in practice: the boot path is proven and the option
surface around it is newer than the boot path. `nix eval` on
`nixosConfigurations.example` is what CI checks, and it catches an
option type error or a stale NixOS interface and nothing else.

If you run it, saying what you exercised and on which NixOS release is
the useful thing to report, in the terms
[../CONTRIBUTING.md](../CONTRIBUTING.md) asks for.
